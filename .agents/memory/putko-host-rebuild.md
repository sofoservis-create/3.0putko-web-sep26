---
name: Putko Host rebuild rules
description: Where the phased Host (hostiteľ) rebuild plan lives and the non-obvious constraints later Host work must keep (navigation, shared listings state, draft resume metadata, async isolation).
---

The plan of record is `.local/tasks/host-product-architecture-audit.md`; each phase gets a "Status" block when it ships, so read that file to see which phase is next.

Rules to keep:
- Host navigation is URL-driven. Never reintroduce transient `activePage`-style state.
- A destination enters primary nav only once its full flow works end-to-end; placeholder tabs return only with their phase.
- The listing editor is never remounted on the `/new` → id URL swap. Every async editor action must bind the editing session and listing id before awaiting and drop its continuation (state updates *and* navigation callbacks) if the session changed or the editor unmounted.
- All Host screens read and mutate accommodations through the single listings store; never add a per-component fetch. Mutations that complete during an in-flight list fetch must win over that fetch's snapshot.
- Draft resume metadata is the `lastVisitedStep` key inside the accommodation JSON payload, not a new API field or column, and it must not affect completion or publishing. The editor's "calendar" step has no server counterpart; it counts as complete when `calendarChoice` is set.
- The Host shell does not render the public header, so it must restore `appLanguage` from localStorage itself or English resets to Slovak on reload.
- Editor saves: a failed save is never retried automatically (the host presses Retry or edits again), and changing steps alone never counts as an unsaved edit. Fields stay editable during in-flight saves, so anything that acts on server completion (review, publish) must first save until the form is clean, and nothing may autosave while the leave dialog offers "Discard".
- Editor numeric controls must never round, clamp, or substitute values on blur (the server accepts any positive finite number, prices carry cents); invalid input gets an inline message from step validation instead.
- Unsaved-change guard lives above the app route Switch (not inside the Host shell) and is decided at render time (the outer Switch renders the guard-held path), not in a `popstate` listener; exits that are not URL changes (mode switch, full-page links) must ask before mutating anything. Reason for render-time: Chromium fires `change`/`blur` on the focused input before `popstate`, and that React render already reads the new URL and unmounts the editor.
- Calendar/availability decision: feed *definitions* live in the accommodation JSON (shared by editor Step 8 and the calendar page); only fetch status and imported dates live in calendar tables. **Why:** one source of truth for what a host configured; status is derived and disposable. **How to apply:** any code that reads feeds must tolerate legacy entries saved without ids (backfill, never filter them out); feeds are fetched on demand only — never claim background sync until a poller exists.
- Calendar feed imports are all-or-nothing: a parse that is not fully understood must fail (keeping the last import), never partially succeed or truncate. **Why:** a successful import replaces every previously imported date, so a truncated, partly parsed or capped feed silently reopens booked nights. **How to apply:** when extending the iCal reader, keep it component-aware and case-insensitive and reject unsupported constructs explicitly instead of skipping them; anything applying a fetched result must also check it is not older than the attempt already recorded.
- "Manual only" (`calendarChoice: none`) means connected links are paused, not deleted, and editing/removing a link never changes the mode. **Why:** hosts flip this from two screens; implicit reconnects on edits surprised reviewers and hosts. **How to apply:** only an explicit add/reconnect sets "connect"; any new consumer of imported dates must ignore them while the listing is not on "connect".
- Outbound fetches of host-supplied URLs must go through the shared public-address fetcher (literal host, every DNS answer, every redirect hop). **Why:** a hostname regex was rejected in review as SSRF-prone. **How to apply:** never add a bare `fetch(url)` for user-provided links.
- The accommodation JSON is edited from two screens (editor and calendar). **Why:** an unlocked read-merge-write or a full-payload editor save silently discarded calendar-page feed changes. **How to apply:** every payload mutation runs under the accommodation row lock, and the editor sends only changed top-level fields; if both screens edit the same field, last writer wins by design.
- Inside the Host shell, `position: sticky` does not work (`<main>` has overflow set) and nothing inside an `animate-fadeIn` wrapper can be viewport-`fixed` (the animation keeps a transform, which becomes the containing block). **How to apply:** render pinned UI outside animated wrappers.
- Photos step uses a validated URL input, not a device upload, because object storage is not provisioned in this workspace; the payload stays `photoUrls` so an upload can be added without a contract change.
- Reservations own their calendar rows: an accepted stay is a calendar block with `source = reservation` written in the same transaction as the status change, under the same accommodation row lock the calendar API takes; calendar block/unblock must never create, merge or delete reservation blocks. **Why:** two writers to the same nights (host blocks vs. guest stays) were the double-booking risk called out in the plan; a single lock order and a single owner per block source keeps calendar and reservations from disagreeing. **How to apply:** stays are half-open (check-in … check-out) while blocks are inclusive (end = check-out − 1) — convert at the boundary; the server sends `stage` + `actions` and the UI renders only those, it never derives what a host may do; requests never expire on their own (a past check-in only offers decline).
- Node tests in api-server import sibling TS files with the `.ts` extension (`rewriteRelativeImportExtensions`), and `pnpm run typecheck:libs` must run before an artifact typecheck after any `lib/db` schema change or the stale `dist` d.ts hides the new columns.
- Host profile vs account: the public Host Profile is stored separately from the shared account row (name, email, phone, password), which Host screens never duplicate or edit. **Why:** one person, one identity; the traveler account owns personal details and `/account` is a traveler-mode screen. **How to apply:** "Account" entries in the Host menu switch to traveler mode and land on `/account`; never build a second personal-details form under `/host`. A first explicit save must persist even if the host accepts the suggested defaults unchanged (only skip the request when a saved profile already exists).
- Payouts stay honest: one shared copy source for editor Step 9 and the payouts page, and the readiness status comes from the server (read-only, "not connected") — no client-side Connect CTA. **Why:** the two surfaces drifted before and a dead Connect button misleads hosts. **How to apply:** Stripe Connect work (separate approval) flips the server status first and derives the UI from it.
- Today is an aggregation, not a store: it fetches one dashboard summary endpoint built from the modules' own rows, and every card/figure links to the module that owns it. **Why:** the plan forbids simulated metrics and duplicated source data. **How to apply:** to add a Today item, extend the pure summary builder (+ its test) and the client task builder; never compute counts client-side from a second fetch, and never add a host-level task that a property filter would hide.
- Messaging decisions: the host is never stored on a conversation (derived from accommodation ownership); each send carries a client-generated key that is unique per thread and reused verbatim on retry, so the server de-duplicates and the client drops the outbox entry once that key comes back from any thread fetch. Unsent text is persisted (outbox + draft) until server confirmation or an explicit host action — a review rejected an in-memory-only outbox and a composer restore that overwrote newer text. Permanent rejections (400/403/404) stay visible with their reason and no Retry; transient failures offer Retry. Read acknowledgments count only after the server confirms and are retried, except on 403/404. Delivery state is derived from the recipient's last-read timestamp. There is no push transport — an open thread polls and the UI says so; don't claim real time.
- Drizzle predicates: never write a raw `sql` template containing "a or b" inside `and(...)` — the fragment is not parenthesised, so the OR escapes the surrounding filters. Use `or(...)` and keep such predicates in a pure helper with injected columns so a dialect-level test can assert the grouping.
- Global CSS pads every `<section>` (marketing pages rely on it) and re-applies the padding for ≤1024px outside any cascade layer, so ordinary padding utilities lose on phones; Host screens using `<section>` need an `!important` override or a non-section element.
- The Host shell is only reachable via traveler login followed by the host-mode switch; any browser verification of Host screens must include that step.

**Why:** the user wants a seamless mobile-first Host flow where each visible section works on phone, tablet, and desktop in SK and EN; earlier shells showed placeholder tabs, lost position on refresh, and stale async responses corrupted other listings.

**How to apply:** before adding a Host screen, add its route, read from the shared store, verify at phone/tablet/desktop widths in both languages, run the Host unit tests, and update the plan's status block.
