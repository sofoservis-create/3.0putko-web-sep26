# Putko.sk — Security, Architecture and Domain Audit

**Audited:** commit `018cfa0` (`Initialize Putko rebuild`), branch `claude/putko-marketplace-audit-h1461w`
**Scope:** whole repository — the live Express/MongoDB API and Next.js front end under `.migration-backup/`, plus the in-progress Vite/Postgres rebuild under `artifacts/` and `lib/`.

---

## Executive summary

1. **The stack is not what the brief describes.** Production is **Express 4 + MongoDB/Mongoose**, not Next.js API routes on Postgres. There are no Server Actions, no route handlers, no Postgres constraints — and no bookings table in the Postgres rebuild at all (`lib/db/drizzle/0000_zippy_eternals.sql`).
2. **`POST /api/auth/change-password` sets any account's password with no authentication** (`Controllers/authController.js:295`). Host ids are published on every listing. This is one request to full host takeover.
3. **`GET /api/hosts/:userId` returns the bcrypt password hash and live `resetPasswordToken`** to anonymous callers (`Controllers/HostController.js:170`); `GET /api/reservation/` returns every booking's guest name, email and phone (`Controllers/ReservationController.js:272`).
4. **28 mutating routes have no authentication**, including all listing CRUD and reservation updates — the latter accepts arbitrary fields, so `paymentStatus: "paid"` and `hostAmountCents` are client-writable.
5. **Double booking is possible.** Availability is a read-modify-write on an embedded array with no transaction, no lock and no constraint (`utils/calendarHold.js:125`); MongoDB cannot express the `EXCLUDE USING gist` guard the brief asks about.
6. **Commission is 1.722 % + €0.31, not 6 %** (`config/payments.js:29`) — €3.97 lost per €100 booking — and every commission invoice carries 23 % VAT despite Putko not being a VAT payer (`utils/superfaktura.js:112`).
7. **Meta Pixel and Microsoft Clarity fire on first paint; no consent mechanism exists anywhere in the repository** (`layout.js:44`, `:60`). Server-side Meta CAPI additionally sends guest email and IP on every booking.
8. **The host-supplied iCal URL is fetched with no scheme, IP, timeout, size or redirect limit** (`AccommodationController.js:1427`) — blind SSRF into the private network, reachable by anyone via an unauthenticated route.
9. **The iCal importer never releases blocks and drops recurring events**, and a cron running **every five seconds** hard-deletes paid bookings without refunding them (`utils/cleanupJob.js:54`, `:106`).
10. Measured, not assumed: **first-load JS is 436 kB gzip on search, 390 kB on a listing, 329 kB on `/login`** — roughly 2.5× the mobile budget, on a mobile-first product.

**Verdict: do not launch.** Items 2–9 are each individually launch-blocking.

## How to read this report

* Ordered by severity, then by blast radius.
* Every finding cites `file:line` against the audited commit. Where a claim could not be settled from code alone it is labelled **UNVERIFIED** with what would settle it.
* Patches are in `audit/patches/`. Each applies cleanly to HEAD on its own (`git apply`); applied as a set, use `git apply --3way` (patch 010 overlaps patch 007 on two route lines).
* Product decisions that must not be made by an auditor are in `audit/DECISIONS-NEEDED.md`.

## The five questions, answered explicitly

**Where is availability computed?**
`.migration-backup/backend/utils/calendarHold.js:37` — `occupiedDays(accommodation)` folds the listing's embedded `occupancyCalendar` array into a `Set` of `yyyy-MM-dd` strings. It is the only availability model, and it is the same array for manual host blocks (`source: 'manual'`), iCal imports (`'ics'`) and confirmed bookings (`'reservation'`) — `models/Accommodation.js:528–556`. Search re-implements the same question independently in MongoDB at `Controllers/AccommodationController.js:1148–1168`, and the two disagree (**H-03**).

**Where is a booking written?**
`Controllers/ReservationController.js:179` — `reservation.save()` inside `createReservation`. Note it takes **no hold**: dates are only claimed later, at `Controllers/PaymentController.js:159` (`holdDates`) when the checkout session is built. The booking becomes real at `utils/calendarHold.js:193` (`confirmHold`), called from `finalizeReservation` (`PaymentController.js:1659`).

**Where is money moved?**
Three places, all on the platform Stripe account:
* charge — `Controllers/PaymentController.js:179` (`checkout.sessions.create`)
* payout — `Controllers/PaymentController.js:1410` (`transfers.create`, destination = the listing's connected account, `metadata.reservationId`, idempotency key `transfer_booking_<id>`)
* refund — `Controllers/CancellationController.js:160` (`refunds.create`, key `refund_booking_<id>`)

The model **is** separate charges and transfers as specified: no `transfer_data`, no `on_behalf_of`, no `application_fee_amount` anywhere; the commission is implicit in transferring `hostAmountCents < totalPriceCents` (`config/payments.js:100`). Only the connected-account capability `transfers` is requested (`utils/stripeHelpers.js:125–162`). **That part is right.** The rate is not (**C-15**).

**Where is the iCal sync loop?**
`Controllers/AccommodationController.js:1391` — `syncBookings()`, scheduled every 3 hours at `index.js:127`. It is sequential over every listing with a feed, with **no lock between runs and no per-feed timeout**, so one hanging feed stalls every listing after it (**C-06**). Export is `generateICS` at `:1254`. The realistic double-booking window against an external channel is the 3-hour interval — unbounded if a feed hangs.

**Where is authorization enforced?**
Unevenly, and that is the story of this audit.
* **Well:** `auth/authorize.js` — `requireReservationAccess` (`:260`) re-derives the actor from whichever grant actually passed rather than from the token's claim; `requireHostSelf` (`:353`) checks the id against the collection, not the claim; `setListingPayoutAccount` (`AccommodationController.js:696`, owner check at `:713`) checks listing ownership and refuses an account the host does not hold. All of `/api/payments/*`, `/api/cancellation/*`, `/api/receipts/*`, `/api/invoices/*` and `/api/dac7/*` are properly guarded.
* **Not at all:** every route on `AccommodationRoutes`, `ReservationRoutes` (except approve/decline), `user.js`, `hostRoutes.js`, `message.js`, `FavoriteRoutes`, `BlogRoutes`, `uploadRoutes`, `CalendarRoutes`.
* **Present but broken:** `restrict()` (`auth/verifyToken.js:29`) fails open (**H-01**), and the guarded `/:id` routes it protects are shadowed by earlier `/:userId` routes anyway (**C-02**).

**Complete list of unauthenticated mutating routes** (28): `POST/PUT/DELETE /api/accommodation`, `/api/accommodation/:id`, `/api/accommodation/:id/images`, `/api/accommodation/:id/occupancyCalendar`, `/api/accommodation/:id/calendar-sync[/:feedId][/status]`, `/api/accommodation/restore/:id`, `/api/accommodation/deleted/:id`, `/api/accommodation/fix-coordinates/:id`, `/api/:accommodationId/occupancy/:entryId`, `/api/accommodation/updateOccupancyCalendar/:userId`, `/api/accommodation/:id/{view,click,interest}`, `/api/reservation`, `/api/reservation/reservations/:id`, `/api/reservation/name/:name`, `/api/reservation/:id`, `/api/reservation/user/:userId`, `/api/reservation/restore/:id`, `/api/reservation/delete/:id`, `/api/users/:id`, `/api/hosts/:id`, `/api/favorite/add`, `/api/favorite/remove/:id`, `/api/blog`, `/api/blog/:id`, `/api/blog-comments/*`, `/api/send`, `/api/addmsg`, `/api/upload-excel`, `/api/chat`.

## Things the code gets right

Worth stating, because the report above is otherwise unrelieved:

* **The cancellation policy IS snapshotted correctly.** `cancellationTiersSnapshot` is written as an expanded array at booking time (`ReservationController.js:116–117`) and refunds read only from it (`utils/cancellationPolicy.js:121`). **No refund path JOINs to the listing.** The CRITICAL finding the brief anticipated is not present.
* **Local accommodation tax is not computed or collected** — `Host.localTaxPerPersonNight` is informational only, exactly as required.
* **The Stripe webhook is solid:** signature verified (`PaymentController.js:292`), claimed atomically against a unique index before handling (`:304`), and released on failure so Stripe's retry genuinely reprocesses (`:332`). Duplicate `checkout.session.completed` is a no-op via a conditional update (`:507`).
* **Transfers and refunds carry deterministic idempotency keys**, so a retry cannot double-pay.
* **Amounts are integer cents end to end** past the quote boundary; `calculateFees` (`config/payments.js:88`) uses `Math.round` throughout.
* **The booking price is server-computed** and a client-supplied `totalPrice` is explicitly stripped (`ReservationController.js:88`).
* **"Request to book" for un-onboarded hosts works as specified** (`utils/requestToBook.js`) — no money is taken until the host confirms and Stripe reports the account payout-ready (`buildCheckoutSession` re-checks at `PaymentController.js:136–145`, so a mailed payment link cannot outlive the host's eligibility).
* **No copyleft exposure.** The only copyleft in either dependency tree is LGPL-3.0 `libvips` under `sharp` (dynamically linked, no distribution) and `caniuse-lite` (CC-BY-4.0, build-time data). No GPL, no AGPL.
* **No N+1 on search.** The results page fires exactly two queries — the paginated list and the map-marker list. The per-listing availability query the brief asks about does not exist; the over-fetch is the uncapped marker query (**M-10**).
* **No raw SQL and no ORM escape hatches.** No `$where`, no `mapReduce`, no `aggregate` with user-controlled stages. The injection surface is regex interpolation (**C-09**, **H-17**, **M-10**), not query construction.
* The Postgres rebuild's auth prototype (`artifacts/api-server/src/routes/test-auth.ts`) is well built — scrypt, hashed session tokens, `timingSafeEqual`, Zod-validated bodies. It is a prototype, clearly namespaced `test-`, and is not the production surface.

## Booking state machine

Statuses are spread across three independent fields, which is itself part of the problem — `isApproved` (`pending`/`approved`/`cancelled`), `paymentStatus` (`unpaid`/`paid`/`refunded`/`partially_refunded`/`failed`) and `payoutStatus` (`pending`/`released`/`failed`), plus `bookingMode` (`instant`/`request`). There is no single status field and no transition guard table; the diagram is in `audit/ARCHITECTURE.md`.

**Illegal transitions the code currently permits:**

| # | Illegal transition | Where | Why it is possible |
|---|---|---|---|
| 1 | `cancelled` → `paid` | `PaymentController.js:507` | `applyPaidCheckoutSession` filters on `paymentStatus: { $ne: "paid" }` only. It never checks `isApproved`. A payment link issued before a cancellation, paid afterwards, sets the booking back to `isApproved: "approved"` and `paid`. |
| 2 | `paid` → `paid` at a different amount | `ReservationController.js:670` | Unauthenticated `updateReservation` writes `totalPriceCents` (**C-08**). |
| 3 | any → `approved` + `paid` with no charge | `ReservationController.js:552–572` | The zero-price branch marks a booking paid and finalises it. Combined with #2, unauthenticated. |
| 4 | `refunded` → `released` | `PaymentController.js:1263–1271` | Guarded by `refundAmountCents > 0` — but that field is client-writable (**C-08**), so clearing it re-opens the payout. |
| 5 | cancel after check-out | `CancellationController.js:108` | No check that check-out has passed. `calculateRefundCents` yields 0 % via the final tier, so no money moves — but the dates are released (`:209`) and a "your booking is cancelled" email goes to a guest who has already stayed. |
| 6 | `released` → cancelled with refund | `CancellationController.js:119` | **Correctly** refused (`already_paid_out`). Listed because it is the one this class of bug usually gets wrong. |
| 7 | hold → confirmed over someone else's dates | `calendarHold.js:203` | Detected and refused after payment, with an admin alert. The guest has already been charged; there is no automatic refund. |
| 8 | `request` → `approved` twice concurrently | `ReservationController.js:739` | Two concurrent approvals both call `buildCheckoutSession` → `holdDates`. Under **C-14** both can hold; patch `011` closes it. |
